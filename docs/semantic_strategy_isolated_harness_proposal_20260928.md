# Prospective agent-process isolation protocol

Status: proposal only. No current or historical gate is reclassified. No invalid case is rerun under this proposal without an explicit new experiment authorization. Qualification remains unused.

The motivation is proven shared interpreter state in the current harness: both agents and the engine share a GC heap, and the frozen V9 opponent calls process-global `gc.freeze()/unfreeze()` at reveals. This can influence another agent's collection work. It does not yet prove that GC caused any particular timeout, nor establish the hosted competition's exact topology. See `semantic_strategy_runtime_heap_audit_20260928.md`.

## Proposed execution

One official kaggle-environments1.32.7 engine stays in the orchestrator. Candidate and opponent each have one separate persistent child interpreter, alive for that game only. Both retain their own normal GC settings. The orchestrator sends only the current player-visible observation and unchanged engine configuration to the appropriate child, then receives its action. The opponent remains the exact frozen responsive V9 package. No replay substitution in a live matchup, scheduling change, future information or policy change is introduced.

Use two dedicated `multiprocessing` spawn children and private Pipes, with explicit absolute frozen project paths and separate working directories. Keep the normal sequential player-call order used by the existing engine. Agents cannot access each other's Python objects or globals. Plain value transport must preserve every observation/configuration field and action type; reconstruct the official observation struct type in each child, rather than invent an attribute-access shim. Log hashes at send, receive and return boundaries. Agent stdout/stderr is captured in the child and returned as diagnostics without sharing the IPC control channel.

Each process starts lazily inside its first normal engine callback. Its process startup, import, source loading, initialization, observation serialization, IPC waiting, action serialization and parent callback work are therefore charged by the existing engine timer. Do not subtract overhead, preload outside the clock, sleep to emulate a charge, extend the time bank or disable the engine limit. Report child load/call time and parent total callback time separately, while the engine's full outer duration controls eligibility. Pass the engine's actual `remainingOverageTime` unchanged. No GC settings change is added by the harness; frozen opponent GC calls affect its own child only.

One game uses three processes, but remains one game worker. Before launch, check memory for all three resident processes plus import peaks; the current3.3GiB free guard may be insufficient and must be measured in the proof. Do not hide memory failure by increasing game concurrency. Destroy only this experiment's known child PIDs after game completion; retain partial artifacts on child exit, exception or timeout. Never reuse a child across games.

## Prospective evidence, before adoption

1. Freeze a new harness directory and manifest. Bind engine version/source hashes, candidate and opponent manifests, transport schema, timers, code and output paths. Bind the same already-used development case as a diagnostic; no qualification seed is accessed.
2. Run one separately authorized serial source control with both saved V12 live06 action streams returned through the new child transports. Require exact all719 actions per seat, all visible-observation hashes, both full ledgers/cash,720engine states and DONE statuses. This tests transport and engine bookkeeping, not policy performance.
3. If authorized next, run unchanged live agents in isolated children on the same development case. Require719calls per seat, original1second allowance and60second overage, both ledgers, no internal errors, no private-state leak, source-module audits in both children and complete diagnostics. Preserve divergent actions and timing failures; do not reuse previous native outcomes as controls unless matching evidence supports it.
4. Measure passive GC callbacks in each child's agent call and the parent callback, including generation, collected count, duration, GC settings, PID and RSS. Keep callback work under the ordinary timer. No `gc.get_objects`, forced collection, freeze, threshold changes or clock exemption. Compare component timing cautiously because even callback overhead and CPU conditions differ.
5. Only after these controls pass and root explicitly adopts a source-bound prospective addendum should a newly labeled development8 screen use this harness. All original shared-process outputs keep their original statuses. A failed8-world screen still prohibits40-world dispatch. No changes to outcome thresholds, opponent identity or case selection accompany isolation.

The first control proves transport equality. A live isolated case tests the revised timing boundary. Neither proves eight-world strength or official-host timing equivalence. Fairness is improved by separating Python heaps and charging all transport/load costs, while remaining uncertainties are explicit.

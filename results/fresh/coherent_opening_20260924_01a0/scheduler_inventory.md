# Scheduler and tape execution inventory

Read-only inventory of reusable APIs for an opening plus same-family continuation with live cash, feed, and wage constraints. No policy or game batch was run.

## Fresh job executor (state-based routes)

Files: `scripts/fragments/segment_job_executor_v3.py` (shared primitives and executor variant), `scripts/fragments/continuation_executor.py` (preferred continuation compiler layered on v3), and older `scripts/fragments/segment_job_executor.py` (integrated older variant). Public entry points in both variants are `segment_executor_start(obs, node)`, `segment_executor_action(obs, state)`, and `segment_executor_status(state)`. Continuation exports `set_deadline(value)` / `check_budget()` for bounded planning. Input `node` has `jobs`, each with relative `day` 0..2, `hour` 0..23, tile coordinate, and command; optional keys include `cash_reserve`, `safety_assets`, `hire_to`, and sparse `start.tiles` signatures.

The continuation compiler delegates shared normalization/validation/pricing primitives to v3: `_own`, `_get`, `_walk`, `_nearest_shed`, `_shed_access`, `_normalise_jobs`, `_failure`, `_check_job`, `_safety_jobs`, `_market_orders`. It freshly routes complete same-tile job chains from *live* `farmer`/`hands` positions and per-worker inventories each day (`_build_day`, `_pack`, `_route_info`); it does not consume donor worker IDs or donor moves. `_preflight` simulates requested hires, using current `farm.money`, `hires_today`, Fibonacci wages, and shed spawn placement, then checks day-0 feasibility. `segment_executor_action` replans each relative day, emits the purchases once with the plan, and records issued jobs/telemetry. V3 similarly routes from live state and has `_preflight`, `_build_day`, `_route`; its route packing is a simpler three-restart chain assignment than continuation's `_pack`.

Job validation covers live tile identity, PLANT/WATER/FERTILIZE/HARVEST, animal care/feed, structure build/place and authorized DIG. Optional automatic `_safety_jobs` protects vulnerable current plants and animals omitted from the job map. Inputs are derived from jobs: PLANT seed counts; FEED consumes WHEAT; FERTILIZE consumes FERTILIZER; animal PLACE consumes the animal. Continuation aggregates existing worker-carried stock into available shed stock before `_market_orders`, then route packing accounts for actual worker inventories and pickup/delivery. V3 market accounting uses private shed stock directly for order sizing; route pickup then considers each worker's inventory.

Cash support is actual-state based per planning call: `_market_orders` subtracts `node.cash_reserve` from current `farm.money`, uses current seed/shed stock and live `observation.market.prices` for quoted products, and returns explicit shortfall failures. Wage checks are actual `farm.money` plus current hires-today Fibonacci sequence during preflight. There is no built-in cross-day cash ledger or explicit reservation for future wages and future feed beyond each day's compiled input orders; `cash_reserve` is a scalar caller-provided floor. Day replanning means a continuation can re-evaluate from realized actual cash/feed, but a coherent opening's future wages/feed need caller-side reserve policy or extended node semantics. V3 and continuation can use arbitrary compatible live farm states/coordinates; they do not require recorded hand indices, although `hire_to` creates a target headcount and an hour-0/1 hire-window constraint applies.

## DSM and Mother-Goose tape replay

`agents/mgt_dsm_a.py` has reusable `Chassis(routes, router=None, settings=None, opponent_plan=None)`, `Chassis.act(observation, configuration=None)`, and `make_agent(routes, router=None, opponent_plan=None, **settings)`. Route actions are indexed by global `step`; router selects a route. `_View` builds a player/config view, while `future_sells`, hand alignment, market guards, and sheep overlay helpers operate around the selected tape. The core is route replay: `act` obtains the observed step and selected route action, and hands correspond to tape list positions. `_hand_align` pads/truncates to current hands; it does not semantically remap each recorded worker's history to a fresh route. Sheep hire logic (`_shp_*`) explicitly reasons about current cash, recorded hire schedule, projected wages and reserved WHEAT/SHEEP, but it is a specialized overlay and tightly bound to tape route/calendar/worker-index semantics.

`scripts/build_mg_tape_agent.py` is the tape-library builder (not `build_mg_tapes.py`, which is absent). Its `main()` reads compressed tape records (`actions` 719, shops, boards, optional `hands_by_step`), deduplicates action payloads, builds the router and embedded route data. With `--normalize-hires`, it uses recorded `hands_by_step` deltas to trim hires to hires that actually arrived, addressing index drift. Optional `--opening` embeds a fixed raw opening route and `opening_until`; generated entry point returns that tape's raw action until the handoff then enters the router/chassis. The builder can combine tape families through `--subs`, but the resulting router chooses tape route histories by its recorded board/shop features.

`scripts/extract_dsm_tapes.py:main()` converts DSM replay JSON into `data/dsm_tapes/56444344/*.json.gz`: per-seat actions, boards, unlocked shops, day-start cash, `hands_by_step` for all 720 observations, and opponent actions. This is recorded evidence/input, not a scheduler. `agents/router_scheduler.py` exposes `Scheduler.__init__`, `.act(obs)`, and module `agent(obs)`. It chooses a public route from observation via a public agent and replaces actions using work-order templates keyed by worker-index strings; `positions = [farmer, *hands]`, so it assumes the original recorded/templated index layout. It has no standalone arbitrary-state job compiler or cash/feed/wage reservation ledger.

## Semantic labor scheduler / tests

`scripts/schedule_semantic_handoff.py:main()` is a research harness, not an online API. It compiles candidate semantic plans, calls `research_labour_profit.choose(live_obs, candidate[:48], "wage", rounds=20)`, substitutes those first 48 actions, and measures exact-engine cash/assets/sales on recorded game/opponent paths. This is a useful precedent for scheduling a fixed short window from a supplied observation, but its candidate actions are worker-index action arrays and it does not reserve feed or purchases.

Known harnesses: `scripts/test_segment_job_executor.py` exercises start/action, job chain ordering, pickup and hire budget failure; `scripts/validate_continuation_executor.py` runs official-engine native reconstruction through `validate_segment_executor.run_node`, trying `hire_to` 11/12/13 and recording exact output/tile parity plus runtime. `scripts/validate_segment_executor.py` is the shared validator. `scripts/build_mg_tape_agent.py` validates generated source compiles and Kaggle's last-callable loader resolves to `mgt_kaggle_entry`. No harness was run for this inventory.

## Direct reuse implications (mechanical)

For a state-compatible coherent opening and continuation, the closest reusable interface is the continuation executor's tile-job schema plus fresh live-state route planning; it already handles arbitrary compatible worker counts, current inventories, feed input, actual cash, and initial wages. It currently plans three relative days per node, so serial same-family windows can share state but have separate node/job lists. Tape replay offers proven opening traces and market/wage guards, while its worker-indexed actions and taped route selection constrain portability. Extracted DSM tape records provide starting-state evidence (cash, board, worker count) and raw openings; the builder has a raw-opening handoff mechanism. Neither the builder nor router_scheduler provides an arbitrary live-state semantic continuation scheduler with a unified multi-day cash/feed/wage reservation interface.
